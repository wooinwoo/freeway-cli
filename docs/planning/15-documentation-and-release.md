# 문서와 설치 배포 및 출시 계획

이 문서는 Freeway를 다른 사용자가 설치해서 사용할 수 있는 제품으로 만들기 위한 작업 범위다. 아래 내용은 설계와 분업 제안이며 실제 외부 배포를 실행했다는 뜻은 아니다. 초기 배포 대상은 로컬 CLI와 게이트웨이이며 공용 추론 서버 운영은 포함하지 않는다.

## 현재 출발점

현재 저장소에는 Windows x64용 `install.ps1`, `bin/freeway.cmd`, Node 기반 실행 코드가 있다. 설치 스크립트는 특정 버전의 ZIP을 내려받고 SHA256을 검사한 뒤 사용자 설치 폴더에 복사하고 PATH를 등록한다. 패키지 버전은 `0.5.0`이고 `package.json`은 `private: true`다.

따라서 배포 경로가 아예 없는 상태는 아니지만, 코드에 설치 스크립트가 있다는 것과 깨끗한 PC에서 전체 설치·업데이트가 검증됐다는 것은 다르다. 기존 흐름을 기준선으로 삼아 검증과 출시 절차를 추가한다.

## 문서를 두 종류로 관리한다

설계 지식창고는 지금의 `docs/planning/`이다. 제품 목적, 공급처 조사, 아키텍처, 요구사항, 결정과 검증 근거를 남긴다. 사용자 docs는 설치하고 실제로 사용하는 방법을 제공한다. 내부 후보 30개를 사용자에게 전부 연결 가능한 공급처처럼 소개하지 않는다.

## 사용자 docs 범위

| 문서 | 포함할 내용 | 주 담당 | 완료 기준 |
| --- | --- | --- | --- |
| README | 제품 목적, 지원 범위, 설치, 첫 실행 | A | 새 사용자가 다음 행동을 알 수 있다 |
| 빠른 시작 | 설치·연결·무료 모델 선택·첫 요청 | A | 깨끗한 환경에서 문서 순서대로 성공한다 |
| 공급처 안내 | 계정·키·공식 로그인·무료 조건·제약 | A | 실제 활성 경로의 지원표와 일치한다 |
| CLI 참고 | 명령·플래그·JSON·종료 코드 | A | 릴리스 도움말과 예제가 일치한다 |
| API 참고 | 인증·요청·응답·스트림·오류·지원 기능 | B | 계약 fixture와 예제가 일치한다 |
| 문제 해결 | 인증 만료·429·경로 없음·버전 오류·네트워크 | A 초안, B 오류 계약 | 오류 코드별 조치가 재현 가능하다 |
| 데이터와 비용 | 저장 위치, 키 보호 범위, 원문 로그, 무료의 의미 | B | 실제 설정과 비용 처리에 근거한다 |
| 개발자 안내 | 실행·검증·어댑터 추가·fixture 작성 | B | 새 공급처를 같은 계약으로 추가할 수 있다 |
| 릴리스 안내 | 변경점·설치 파일·업데이트·복구·알려진 제한 | B 초안, A 설치 확인 | 실제 배포 버전과 일치한다 |

최초에는 저장소의 Markdown과 CLI 도움말로 충분하다. 문서 사이트용 프레임워크와 별도 호스팅을 필수 작업으로 만들지 않는다. 사이트를 만들더라도 같은 원본을 사용하고 공개 예제에 비밀을 넣지 않는다.

## 기능과 docs를 함께 완료한다

공급처를 추가하는 PR에는 지원 모델·무료 근거·연결 방법·제약·계약 fixture를 포함한다. API 변경에는 요청·응답 예시와 오류 설명을 포함한다. CLI 명령을 추가하면 도움말과 빠른 시작의 영향을 확인한다.

작동하지 않는 예제를 다음 단계 문서로 남기지 않는다. 계획 중 명령은 계획 문서에만 표시하며 사용자 설치 안내에는 실제 릴리스에서 동작하는 명령만 넣는다.

## 배포 경로 선택

| 경로 | 용도 | 추가 작업 | 초기 판단 |
| --- | --- | --- | --- |
| Windows ZIP과 PowerShell 설치 | 기존 Windows x64 배포 유지 | 체크섬·설치·PATH·업데이트·제거 시험 | 우선 검증 |
| Node 소스 또는 패키지 | Node가 있는 개발자 환경 | 포함 파일·엔트리·지원 Node 버전 정리 | 대안으로 검증 |
| npm과 npx | 명령 한 번으로 실행·설치 | 패키지 공개 설정, 이름, 런타임·바이너리 전략 | 선택 후 구현 |
| Go 또는 Rust 바이너리 | 언어 전환 시 단일 실행 파일 | OS·CPU 빌드, 배포·서명·호환성 | 전환 결정 이후 |
| Linux·macOS 패키지 | 지원 OS 확장 | 각 OS 설치·권한·프로세스·인코딩 시험 | 대상 확정 후 |

`npx`는 배포 방법이며 내부 언어를 결정하지 않는다. 현재 패키지를 바꾸지 않고 이미 npm 공개 배포가 가능하다고 안내하지 않는다. 모든 배포 방식을 한 번에 지원하는 것도 초기 완료 조건이 아니다.

## 빌드 산출물

하나의 버전은 소스 커밋, 패키지 버전, CLI 버전, 릴리스 태그, 산출물 이름, 체크섬이 일치해야 한다. 자동화가 릴리스용 파일 목록을 명시적으로 구성하게 하고 개발 폴더 전체를 압축하지 않는다.

| 포함 | 제외 |
| --- | --- |
| 실행 코드와 필요한 정적 자산 | `.env`, `.data`, 키·토큰·쿠키 |
| 설치와 제거에 필요한 파일 | 대화 이력·실제 사용자 설정 |
| 번들 런타임과 해당 라이선스 | 로그·캐시·개발용 임시 산출물 |
| 버전 정보·라이선스·릴리스 안내 | 개인 계정 ID·로컬 인증 저장소 |

Node를 번들하면 해당 OS·CPU에 맞는 런타임과 라이선스를 함께 검증한다. 체크섬은 파일의 일관성을 확인하지만 그 자체로 배포자의 신원을 증명하는 서명은 아니다. 서명과 출처 검증은 실제 배포 방식에 맞춰 별도로 선택한다.

## 설치와 상태 저장을 분리한다

애플리케이션 실행 파일과 사용자 데이터는 분리한다. 업데이트는 사용자 인증·설정·이력을 덮어쓰지 않아야 한다. 제거 시 프로그램만 제거할지 데이터까지 지울지 명확히 구분하고, 데이터 삭제는 별도 사용자 동작으로 둔다.

### 기존 설치의 데이터 이전

현재 기본 데이터 위치는 설치 루트의 `.data`이며, `FREEWAY_DATA_DIR`로 다른 위치를 사용할 수 있다. 새 데이터 위치로 전환할 때는 기존 설치의 실제 설정과 이 두 경로를 먼저 확인한다. 사용자 지정 경로를 무시하거나 비어 있는 새 경로를 만들었다는 이유로 기존 데이터가 없다고 판단하지 않는다. 후보가 여러 개면 자동 병합하거나 덮어쓰지 않는다.

게이트웨이를 종료하고 데이터 폴더 잠금을 확보한 뒤 `vault.key`, `state.json`, `chats.json` 등 해당 데이터 디렉터리 전체를 일관된 상태로 백업·복사한다. `vault.key`를 새로 생성하면 기존 인증값과 대화를 복호화할 수 없으므로 키와 암호문을 한 단위로 취급한다. 백업과 새 경로에도 기존 접근 제한을 적용한다.

새 위치에서 설정 로드와 기존 인증·대화의 복호화를 확인한 뒤에만 사용 경로를 전환한다. 실패하면 원본을 그대로 두고 이전 경로로 복구한다. 마이그레이션과 스키마 변환을 동시에 수행할 경우 각 단계의 원본과 복구 지점을 구분한다. 설치·업데이트 시험에는 비어 있지 않은 실제 형식의 암호화 데이터와 사용자 지정 데이터 경로를 포함한다.

게이트웨이가 실행 중인 상태의 업데이트는 파일 교체와 프로세스 정리를 다뤄야 한다. 초기 버전에서는 실행 중 업데이트를 감지해 종료 후 재시도를 안내하는 단순한 방식도 가능하다. 사용자가 띄운 다른 OpenCode·Cline 프로세스를 포괄 종료하지 않는다.

## 업데이트와 이전 버전 복구

1. 현재 버전과 대상 버전, 변경되는 데이터 형식을 확인한다.
2. 새 산출물을 임시 위치에서 내려받고 체크섬을 확인한다.
3. 프로그램을 종료한 뒤 버전 단위로 교체한다.
4. 기동·설정 로드·모델 목록·가벼운 진단을 확인한다.
5. 실패 시 이전 프로그램 버전으로 복구할 수 있게 한다.

데이터 스키마를 바꾸는 버전은 파일 백업과 복구 절차도 필요하다. 프로그램 바이너리만 되돌려도 새 스키마 데이터를 이전 버전이 읽을 수 있다고 가정하지 않는다. 무료 카탈로그 갱신과 프로그램 업데이트도 별개로 취급한다.

## CI 범위

PR 검사는 네트워크나 개인 키 없이 요청 검증, 라우팅 계획, 예약 경쟁, 스트림·도구 fixture, 오류 분류, 비밀 마스킹, 문서 링크와 예제를 확인한다. 외부 무료 API의 가용성 때문에 모든 PR이 흔들리게 하지 않는다.

실제 공급처 시험은 인증이 제공된 별도 환경에서 제한적으로 수행한다. 외부 기여 PR에 비밀을 주입하지 않는다. 빌드 작업은 명시한 파일로 릴리스 후보를 만들고, 패키지 포함 파일과 버전을 검사한다. 대상 OS별 설치 시험은 준비된 깨끗한 환경에서 수행한다.

현재 저장소의 테스트 명령이 참조하는 파일 일부는 추적 파일 목록에 없으므로, CI가 실제로 실행할 검증부터 갖춰야 한다. 존재하지 않는 검사 명령을 녹색 게이트로 대신하지 않는다.

## 기능별 출시 분업

최종 작성 책임과 인계 조건은 [제품 공백과 책임 계약](17-product-gap-and-ownership.md)을 따른다. A가 패키지 파일 목록·런타임 구성·패키징 명령·설치기를 작성하고, B는 CI에서 그 명령을 실행해 버전·파일 목록·비밀 제외·체크섬을 검증한다. 데이터 이전과 스키마 복구는 B가 작성하며 A가 설치 흐름에 연결한다.

| 역할 | A | B |
| --- | --- | --- |
| 사용자 여정 | 설치·연결·모델 선택·오류 복구 | API와 상태의 일관성 |
| 문서 | README·빠른 시작·공급처·CLI·설치 | API·개발자·데이터·비용·릴리스 |
| 산출물 | 포함 파일 목록·패키징 명령·런처·설치·업데이트·제거 | CI 빌드 실행·버전·파일 목록 검증·체크섬 |
| 검증 | 깨끗한 환경 설치와 실사용 | 계약·동시성·비용·상태 복구 |
| 최종 게시 | 사용자 문서·지원표·설치 수락 결과 제출 | 후보 산출물·검사 결과 확인과 게시 담당 |

최종 릴리스는 두 영역이 모두 통과해야 한다. A와 B가 각각 별도의 배포 패키지를 만드는 대신 같은 버전과 릴리스 체크리스트를 사용한다. 실제 외부 게시와 레포 공개 설정 변경은 해당 작업을 요청받았을 때 수행한다.

## 출시 완료 기준

- 문서만 보고 설치·연결·무료 요청·실패 복구를 재현한다.
- 선언한 지원 OS에서 실행·취소·업데이트·복구·제거를 확인한다.
- 기존 기본 `.data`와 사용자 지정 경로의 인증·설정·대화를 보존하며, 키·암호문 이전 실패 시 원본으로 복구한다.
- API·CLI 도움말·공급처 지원표가 실제 바이너리와 일치한다.
- 활성 경로의 무료 근거와 기능 검증 결과가 있다.
- 유료 대체와 보조 요청 비용을 기본 정책이 통제한다.
- 배포 파일에 키와 사용자 데이터가 없고 체크섬이 일치한다.
- 알려진 제한과 복구 방법을 릴리스 안내에서 찾을 수 있다.

## 기존 단계와 연결

M0는 무료 경로와 인터페이스 검증이다. M1부터 계약·오류·개발자 문서를 같이 쓴다. M2는 CLI와 사용자 docs를 함께 마무리한다. 테스트 배포를 M2의 검증에 포함하며, 이후 추가 공급처나 언어 전환은 같은 설치·복구 기준을 다시 통과한다. 배포를 M4까지 미루는 전제로 해석하지 않는다.
