# 라우팅 정책과 한도 관리 설계

## 선택의 우선순위

초기 라우팅은 설명 가능한 규칙으로 구현한다. 별도 LLM 판단을 기본 경로에 넣지 않는다. 무료 모델을 선택하면서 유료 판단 모델을 호출하는 비용을 피하고, 같은 상태에서 선택을 재현하기 위해서다.

후보 생성과 실행은 분리한다. 계획 생성은 외부 추론 없이 현재 카탈로그와 상태만 읽어 실행 가능한 경로와 제외 이유를 반환한다.

## 먼저 제거할 후보

아래 순서로 검사한다. 제거 이유는 경로별로 남기며, 최종 오류의 원인이 될 수 있다.

1. 사용자가 비활성화한 공급처 또는 허용하지 않은 모델.
2. 미인증, 인증 만료, 현재 계정 권한이 확인되지 않은 경로.
3. 유료이거나 무료 근거가 만료된 경로.
4. strict-free에서 추가 비용을 통제할 수 없는 CLI 또는 보조 호출 경로.
5. 요청의 실행 계약과 맞지 않는 경로.
6. 도구 호출·입력 형식·컨텍스트·출력 길이를 충족하지 못하는 경로.
7. 활성 쿨다운 또는 실제·예약 합산 한도에 걸린 경로.
8. 같은 요청에서 이미 실패했거나 전체 시도 예산을 넘기는 경로.

기능이 `unknown`인 경로를 기능이 필요한 요청에 넣지 않는다. 텍스트 요청은 도구 지원 여부가 unknown인 직접 API로 보낼 수 있지만, 도구 요청은 확인된 경로로만 보낸다.

## 정렬 규칙

설명 가능성을 위해 초기에는 하나의 복잡한 점수 대신 아래 우선순위 튜플을 제안한다.

```text
모델 고정 정책 충족 여부
사용자 모델 선호 순서
무료 할당의 사용 가능 상태
사용자가 지정한 공급처 우선순위
최근 성공 상태
충분한 표본이 있는 경우의 지연 순위
안정적인 경로 ID
```

한도 기반 자동 배분을 켠 경우, 같은 선호 등급 안에서 임박한 리셋·남은 할당 비율·관측 신뢰도를 사용할 수 있다. 서로 다른 단위의 요청 수와 토큰 수를 그대로 더하지 않는다. 사용자가 특정 공급처를 우선하도록 고정한 정책은 자동 점수가 몰래 뒤집지 않는다.

한도가 unknown이면 기본적으로 알려진 안전한 경로 뒤에 두되, 사용자가 unknown 경로를 포함하도록 선택할 수 있다. 잔여량 unknown을 0 또는 무한대로 변환하지 않는다.

## 요청 선택 모드

| 모드 | 허용되는 변화 | 실패 시 동작 |
| --- | --- | --- |
| exact route | 모델과 경로 모두 고정 | 해당 경로 오류를 반환한다 |
| exact model | 같은 모델 정체성이 확인된 경로 변경 | 같은 모델 경로가 없으면 종료한다 |
| free auto | 사용자 허용 모델과 경로 사이 이동 | 전체 예산 안에서 다음 후보를 시도한다 |
| agent task | 외부 작업 실행기 선택 | 진행 중 에이전트의 상태 이식은 하지 않는다 |

같은 제조사의 비슷한 이름은 exact model이 아니다. 경로가 제공하는 모델이 이동 별칭이라면 snapshot을 알 수 있는지 기록하고, 모르면 고정 버전 보장을 하지 않는다.

## 한도 데이터

```text
scopeKey: 공급처와 계정 또는 IP 및 모델 풀의 범위를 식별한다
unit: requests, input_tokens, output_tokens, total_tokens, credits, neurons
windowKind: fixed, rolling, provider_defined, unknown
windowStart 및 resetAt: 근거가 있을 때만 기록한다
limit: 공식 또는 사용자 설정 상한
reportedUsed 및 reportedRemaining: 공급처 조회 값과 관측 시각
localUsed 및 reserved: 이 게이트웨이의 사용량과 진행 중 예약
confidence: authoritative, observed, estimated, unknown
```

사용자 설정 상한은 추가적인 로컬 안전 장치다. 공급처가 보장한 상한으로 표시하지 않는다. 공급처 값은 다른 클라이언트 사용과 캐시 지연 때문에 오래될 수 있으므로 `observedAt`을 함께 보여 준다.

## 예약 알고리즘

한도 판정과 예약 생성은 같은 원자적 작업 안에서 수행한다. 사용 가능 여부를 읽은 뒤 외부 호출을 시작하고 나중에 요청 수를 늘리는 방식은 동시에 들어온 요청에서 초과가 발생한다.

```text
입력 요청의 예상 비용과 한도 소비를 계산한다
직렬화된 상태 변경 구간에 들어간다
창과 예약 상태를 갱신한다
현재 실제 사용량과 활성 예약을 합쳐 상한을 검사한다
허용되면 고유한 예약 ID를 기록한다
상태를 내구성 있게 저장한다
외부 요청을 시작한다
결과 또는 불확실한 종료 상태를 예약 ID로 한 번만 확정한다
```

요청 수 한도는 요청을 보낸 시점에 소비됐다고 보수적으로 본다. 공급처가 실패 요청을 계산하지 않는다는 근거가 있을 때만 정산 정책을 바꾼다. 타임아웃이 발생했다고 무조건 예약을 환불하면 이미 처리된 요청을 중복 사용하게 된다.

## 토큰 예약

예상 입력과 최대 출력을 합산하는 것은 상한 보호에 유용하지만 공급처 토크나이저와 차이가 있다. 현재 코드의 문자 수 기반 추정치는 실제 토큰 수와 구분해야 한다. 도구 정의·이미지·추론 토큰도 한도에 포함되는지는 공급처별로 다르다.

실제 usage가 오면 추정 예약을 실제 소비로 대체한다. usage가 없거나 통신이 끊기면 추정 소비를 남기고 신뢰도를 낮춘다. 공급처 조회를 통해 더 정확한 전체 사용량을 얻으면 원본 관측과 로컬 이벤트의 중복 합산을 방지한다.

## 공급처 누계와 로컬 기록의 정산

각 로컬 소비 이벤트에 고유 ID, quota scope, 창 ID, 단위, 전송 시각, 공급처 확인 여부를 기록한다. 공급처 스냅샷에는 조회 시각과 공급처가 제공한 측정 시각, 포함 범위 또는 watermark를 구분해 저장한다. 응답을 받은 시각만으로 모든 이전 로컬 호출이 스냅샷에 포함됐다고 가정하지 않는다.

공급처가 요청 ID나 sequence 등으로 포함 범위를 보장하는 경우에는 다음 규칙을 사용한다.

```text
예약에 사용할 소비량 = 공급처 누계
                    + 포함 범위 밖에서 확정된 로컬 소비
                    + 스냅샷에 포함되지 않은 활성 예약
```

로컬 이벤트를 포함됨으로 표시하는 기준은 공급처의 명시적 계약이다. 스냅샷이 이미 포함한 로컬 5회에 공급처 누계 10회가 있다면 소비는 10회이며 15회가 아니다. 동일 스냅샷을 다시 받거나 완료 이벤트가 중복 도착해도 결과가 바뀌지 않아야 한다.

포함 범위를 제공하지 않는 공급처에서는 정확한 정산이 불가능할 수 있다. 기본 보호 계산은 `공급처 누계 + 포함됐다고 증명하지 못한 로컬 소비 + 미포함 예약`으로 두고 추정으로 표시한다. 이 계산은 로컬 소비를 중복 계산해 일찍 차단할 수 있다. 다른 도구의 조회 이후 사용량까지 아는 값도 아니므로 전체 실제 사용량의 확정 상한이라고 부르지 않는다.

포함 범위가 unknown인 값을 매번 덮어써 로컬 기록을 지우지 않는다. 반복 조회 자체로 로컬 소비를 증가시키지도 않는다. 근거 없는 차단은 `local_budget_guard`로 표시하며, 공급처가 확정한 `quota_exhausted`와 구분한다. 활성 예약이 있는 상태의 늦은 스냅샷, 계정 외부 사용, 창 리셋, 재조회 중복을 정산 시험에 포함한다.

## 실패 분류와 후속 동작

| 오류 | 상태 변경 | 같은 요청의 다음 행동 |
| --- | --- | --- |
| 잘못된 요청 형식 | 요청 실패 | 다른 모델로 숨기지 않고 종료한다 |
| 미지원 기능 | 해당 경로 기능 재검토 | 요청이 유효하고 다른 호환 경로가 있으면 시작 전 대체한다 |
| 401 또는 토큰 만료 | 연결 재인증 필요 | 해당 연결을 제외하고 허용된 다른 연결을 시도한다 |
| 403 권한·정책 | 권한 또는 정책 차단 | 원인을 구분하고 무조건 일시 쿨다운으로 처리하지 않는다 |
| 402 잔액 부족 | 유료 또는 계정 권한 문제 | strict-free에서는 유료 충전 안내로 자동 전환하지 않는다 |
| 429 | 적용 범위의 제한과 리셋 기록 | 시작 전 다음 독립 경로를 시도한다 |
| 5xx | 일시 장애 관측 | 남은 시간과 횟수 안에서 대체한다 |
| 첫 이벤트 전 연결 실패 | 시도 실패 | 요청 소비 여부를 보수적으로 기록하고 대체한다 |
| 스트림 중 오류 | 부분 응답 실패 | 같은 요청에서 다른 모델로 이어 쓰지 않는다 |
| 사용자 취소 | 취소됨 | 대체하지 않는다 |

HTTP 상태만으로 무료 쿼터 소진과 분당 제한을 구분하기 어렵다. 공식 error code와 `Retry-After`가 있으면 우선 사용하고, 모르면 짧은 제한 상태를 부여하되 일일 소진으로 단정하지 않는다.

## 쿨다운과 복구

공급처가 준 리셋 시각과 Retry-After를 우선한다. 없으면 제한된 기본 대기와 지수 백오프를 사용한다. 요청마다 독립적으로 긴 대기를 실행하지 말고 경로 상태에 다음 시도 시점을 기록한다. 동시 요청이 같은 경로를 한꺼번에 재시험하지 않도록 복구 시도 수를 제한한다.

프로세스가 재시작되면 마지막 한도 관측과 활성 예약을 읽는다. 전송 여부를 모르는 시도는 즉시 무료로 되돌리지 않고 불확실한 소비로 복구한다. 오래된 프로세스가 살아 있는지 확인하기 전에 그 프로세스의 예약을 모두 지우지 않는다.

## 스트림 시작 기준

초기에는 정규화된 이벤트 하나라도 클라이언트에 전달하면 커밋된 응답으로 취급한다. 텍스트 글자만 기준으로 삼으면 role, tool ID, 도구 인자 일부가 이미 나갔는데도 다른 모델로 전환하는 문제가 생긴다.

스트림 상태는 `not_started`, `committed`, `completed`, `failed_after_commit`으로 구분한다. 출력이 시작된 요청에서 허용되는 복구는 중단 사실 표시와 사용자의 새 재생성 요청이다.

## 선택 이유 예시

```json
{
  "policy": "preferred-free",
  "selectedRoute": "opencode/deepseek-v4.1-flash-free",
  "reasons": ["preferred_model", "free_entitlement_verified", "ready"],
  "skipped": [
    {"route": "requesty/muse-glimmer-30b", "reason": "model_fixed"},
    {"route": "openrouter/deepseek-v4.1-flash", "reason": "paid_model"}
  ],
  "quota": {"remaining": null, "confidence": "unknown"}
}
```

이 예시는 설계 계약이며 두 경로가 실제로 같은 추론 기능을 제공한다는 실행 증거는 아니다. 브리지의 기능이 텍스트로 제한되면 explain 결과의 대상 요청도 텍스트로 제한한다.

## 라우팅 시험의 최소 집합

같은 모델 경로 변경, 모델 고정 위반 방지, Auto의 다른 모델 전환, 도구 미지원 제거, 유료·불명 가격 제거, 갱신 중 카탈로그, 한 자리 할당의 경쟁, 날짜 경계, 롤링 창, 시계 역행, 취소, 중복 확정, 스트림 후 오류를 포함한다. 네트워크에 의존하는 공급처 시험과 가짜 시계·상태로 하는 정책 시험을 구분한다.
