# 구현 범위와 협업 계획

## 구현 원칙

초기에는 기존 Node POC를 검증 도구와 동작 기준선으로 사용한다. 공급처 개수를 먼저 늘리기보다 대표 무료 경로와 API 계약을 확정한다. 구현 단계는 달력상의 약속이 아니라 앞 단계의 검증 결과를 통과해야 다음 단계로 넘어가는 게이트다.

## 단계별 범위

| 단계 | 목적 | 필수 산출물 | 완료 게이트 |
| --- | --- | --- | --- |
| M0 | 무료 경로의 실현 가능성 | OpenCode DeepSeek, Cline, Requesty Muse의 조사·호출·비용·기능 기록 | 대표 경로의 계약과 차별점이 증명됨 |
| M1 | 안전한 라우팅 코어 | 경로 모델, 정책 계획, 예약, 오류 분류, 직접 API 계약 시험 | 유료 차단·동시성·스트림 경계 통과 |
| M2 | 대표 브리지와 CLI 사용성 | 검증된 OpenCode 또는 Cline 경로, 연결·경로·한도·설명 UI, 사용자 docs와 테스트 배포 | 문서에 따라 설치·사용·업데이트·복구 가능 |
| M3 | 추가 공식 API와 품질 개선 | NVIDIA·Requesty·Z.ai 등 검증된 추가 경로, 계정 조회 | 공급처별 계약 시험과 비용 근거 통과 |
| M4 | 언어·배포·확장 재평가 | 필요할 경우 Go 코어 또는 Rust TUI 실험, OS 패키징 | 동작 보존과 유지비 개선이 입증됨 |

M0에서 발견한 경로가 모두 기존 도구 설정으로 충분하다면 M1을 축소한다. M0 결과가 부정적이어도 공급처 목록을 늘려 프로젝트를 계속하는 것을 기본 동작으로 삼지 않는다.

## M0의 구체적 작업

| 작업 | 완료 증거 | 관련 요구사항 |
| --- | --- | --- |
| OpenRouter 기본·BYOK 범위 분석 | 현재 API·공식 계약·대체 시험 | FR 011, FR 012, FR 017 |
| OpenCode 무료 DeepSeek 검증 | 실제 모델 ID·CLI 버전·응답·비용·쿼터 관측 | FR 002, FR 003, FR 009 |
| Cline 무료 경로 검증 | 공식 CLI 자동화·인증·무료 모델·결과 | FR 002, FR 004, FR 028 |
| Requesty Muse 검증 | 정확한 변형·키·직접 API·무료 상한·결과 | FR 001, FR 003, FR 007 |
| 추가 호출 여부 확인 | 타이틀·요약·판단·플러그인별 사용량 | FR 017, FR 035 |
| 기능 보존 조사 | 메시지·툴·스트림·취소별 지원표 | FR 014, FR 024, FR 026 |

계정이 연결되지 않은 후보는 보류 상태로 남겨도 설계 초안은 작성할 수 있다. 다만 해당 경로가 제품 완료 조건에 필수이면 M0 게이트는 아직 통과하지 못한 것으로 판단한다.

## M1의 최소 구현 단위

1. `Route`와 `Entitlement` 데이터를 기존 카탈로그에 추가한다.
2. 현재 후보 생성에서 외부 요청이 없는 라우팅 계획을 분리한다.
3. 기능·비용·권한·한도를 후보 제거 사유로 반환한다.
4. 요청별 예약과 시도 기록을 한 번만 확정한다.
5. 기존 HTTP 어댑터 두 개로 스트림·도구·오류 fixture를 통과시킨다.
6. 기존 호환 API에 검증된 경로만 노출한다.
7. 기존 CLI에서 explain과 경로 상태를 조회한다.

처음부터 수십 개의 어댑터 플러그인과 범용 정책 언어를 만들지 않는다. 실제 두 경로가 요구하는 차이를 확인한 뒤 공통 계약을 추출한다.

## 두 작업자의 책임

최종 작성 책임과 인계·결함 수정 책임은 [제품 공백과 책임 계약](17-product-gap-and-ownership.md)을 기준으로 한다. 아래 표는 요약이며, 공동 검토를 공동 작성 책임으로 해석하지 않는다. A는 공급처 연결·어댑터·CLI·설치기를 작성하고, B는 공통 계약·라우팅·한도·API·비밀 저장·데이터 이전·CI·릴리스를 작성한다. 태스크 수준에서는 [계층별 작업 분해](16-work-breakdown.md)의 단일 담당자를 따른다.

| 영역 | 작업자 A | 작업자 B |
| --- | --- | --- |
| 공급처 조사 | 주 담당 | 수용 기준 검토 |
| 공식 인증·모델 목록·프로토콜 | 주 담당 | 계약 검토 |
| 어댑터 구현·fixture | 주 담당 | 경계 입력 검토 |
| 라우팅 정책·후보 정렬 | 입력 데이터 제공 | 주 담당 |
| 한도·예약·쿨다운 | 공급처 의미 정의 | 주 담당 |
| API·오류·스트림 실행기 | 어댑터 결과 연결 | 주 담당 |
| CLI·TUI | 주 담당 | 상태 API 제공 |
| 대화·작업 상태 | 외부 CLI 상태 조사 | 공통 상태 계약 주 담당 |
| 통합 검증 | 공급처 실제 시험 | 코어 회귀·경쟁 시험 |
| 사용자 docs | 빠른 시작·공급처·CLI·설치 | API·개발자·데이터·비용 |
| 설치·패키징 | OS별 설치·업데이트·제거와 사용자 검증 | 상태 보존·버전 복구 검토 |
| CI·릴리스 | 깨끗한 환경 설치 확인 | 빌드·자동 검사·체크섬·릴리스 안내 |

A가 맡는 라우팅 관련 작업은 공급처의 호출 방법·한도 의미·기능을 제공하는 데까지다. 어느 경로를 선택할지 결정하는 정책은 B가 맡는다. 원래 대화의 A와 B 양쪽에 있던 라우팅 책임을 여기서 분리한다.

docs와 첫 테스트 배포는 M2까지의 제품 작업이다. M4의 OS 패키징은 기존 출시를 미루는 단계가 아니라 추가 OS나 언어 전환 시 재검증을 뜻한다. 구체적인 산출물과 출시 게이트는 [문서와 출시 계획](15-documentation-and-release.md)을 따른다.

## 두 작업자의 교환 계약

A는 경로 ID, 모델 정체성, 인증 상태, 무료 근거, 기능, 한도 범위, 오류 분류, 기록된 입출력을 제공한다. B는 이를 받아 선택 계획, 예약, 실행 결과, 상태 변경, explain 출력을 제공한다.

공통 파일을 동시에 수정하지 않도록 모델·오류·이벤트 계약을 먼저 합의한다. 어댑터는 B의 정렬 정책을 호출하지 않으며, UI는 어댑터별 HTTP 요청을 직접 만들지 않는다. 한 공급처 추가가 라우팅 코어 전체의 조건문 수정으로 이어지면 계약을 다시 검토한다.

## 통합 순서

```text
계약 예시와 fixture 합의
  코어의 가짜 어댑터 시험
  첫 실제 공급처 연결
  두 번째 독립 경로 연결
  실패 전 대체와 취소
  CLI 연결과 설명 화면
  실제 무료 사용량과 비용 확인
```

첫 통합에서 고급 TUI와 다중 프로세스를 동시에 도입하지 않는다. 어디에서 실패했는지 구분할 수 있도록 계약·실행·사용 화면을 순차적으로 검증한다.

## 언어 선택

| 선택지 | 장점 | 추가 비용 | 판단 기준 |
| --- | --- | --- | --- |
| 기존 Node 유지 | POC 재사용, 기존 설치 흐름 유지 | 바이너리·런타임 배포 관리 | 가장 빨리 대표 경로를 검증하는가 |
| Go 코어 | 단일 바이너리와 서버 구현 경험 | 재작성, 기존 동작·패키징 회귀 | 팀의 명확한 학습 목표와 구현 책임이 있는가 |
| Rust TUI | 터미널 UI 생태계와 세밀한 제어 | 별도 언어, IPC·릴리스 조합 | 기존 TUI의 구체적 한계를 해결하는가 |
| Go 코어와 Rust TUI | 계층별 도구 선택 | 빌드·프로토콜·배포가 가장 복잡 | 두 언어 분리가 실제 이득을 증명하는가 |

기본 제안은 M0와 M1 동안 Node를 유지하는 것이다. 팀이 학습을 위해 Go 또는 Rust를 선택할 수 있지만, 그 선택을 라우팅 문제의 필수 해결책이라고 설명하지 않는다. 언어를 바꾸더라도 API·어댑터 fixture와 요구사항은 그대로 사용한다.

## 초기 제외 범위

- 공용 무료 API 서비스, 결제·구독 판매, 조직 계정 관리.
- 모든 30개 후보의 동시 구현.
- 무제한 무료 사용 보장과 다중 계정으로 한도 확장.
- 진행 중 코딩 에이전트의 내부 상태 자동 이식.
- 이미지·오디오·비디오·임베딩 전체 호환.
- Responses와 Anthropic Messages의 완전 구현.
- 플러그인 마켓, 원격 워커, 분산 데이터베이스.
- 측정 근거 없는 성능 순위와 유료 LLM 기반 기본 라우팅.

## 범위 변경 규칙

새 기능을 추가하려면 해결할 사용자 시나리오, 현재 경로로 해결되지 않는 이유, 요구사항 ID, 단계, 검증 방법을 함께 적는다. 공급처가 하나 추가됐다는 이유만으로 새 서버나 새 정책 언어를 만들지 않는다.

## 회의에서 확정할 항목

1. 주 사용 환경과 우선 지원 OS.
2. 첫 제품의 중심이 호환 API인지, 자체 채팅인지, 외부 에이전트 위임인지.
3. DeepSeek의 정확한 버전과 Muse의 원하는 변형.
4. 다른 모델 자동 전환 허용 범위와 품질 저하 허용 여부.
5. 계정 연결이 필요한 대표 공급처와 담당자.
6. 언어 학습 목표를 별도 실험으로 둘지 제품 구현에 포함할지.

이 항목을 답해야만 모든 작업이 시작되는 것은 아니다. 기본 로컬·무료·기존 코드 재사용 가정으로 조사와 계약 검증을 먼저 진행할 수 있다.
