# OpenRouter에서 남는 문제와 Freeway의 역할

## 먼저 결론

Freeway의 제품 가설은 **여러 서비스에 흩어진 개인의 무료 사용 경로를 연결하고, 그 경로의 인증·한도·지원 기능을 기준으로 사용할 곳을 선택하는 로컬 도구**다. OpenRouter 안의 모델 자동 전환만 필요하다면 OpenRouter를 사용하면 된다.

실제 호출에서는 OpenRouter의 무료 응답과 무료 대체가 성공했다. OpenCode 무료 DeepSeek는 할당 소진 메시지를 반환했다. Cline의 해당 무료 모델은 model not found를 반환했고 공식 CLI는 프로모션 종료 안내를 표시했다. 따라서 외부 경로의 연결뿐 아니라 현재 사용 가능 상태를 관리하는 일을 제품 범위로 잡는다. [실증 결과](19-live-validation.md)

## OpenRouter가 이미 해결하는 것

OpenRouter는 통합 API, 모델 대체, 공급처 선택·정렬, BYOK 키 우선순위와 실패 시 다음 키 시도를 제공한다. 무료 모델 선택도 제공한다. 따라서 “OpenRouter는 수동이고 우리는 자동이다”, “OpenRouter는 한도 초과 시 대체할 수 없다”는 설명은 차별점으로 사용하지 않는다. [공급처 선택](https://openrouter.ai/docs/guides/routing/provider-selection), [BYOK](https://openrouter.ai/docs/guides/overview/auth/byok), [무료 모델](https://openrouter.ai/collections/free-models)

또한 OpenRouter에는 자신의 키·예산·무료 모델 일일 한도를 조회하는 API가 있다. “한도 조회 기능이 없다”는 주장도 하지 않는다. Freeway가 추가하려는 것은 OpenRouter 바깥 서비스의 관측까지 합친 개인의 사용 가능 상태다. [한도 조회](https://openrouter.ai/docs/api_reference/limits)

## 우리 사용 목적에서 남는 문제

| 문제 ID | 사용자가 겪는 문제 | OpenRouter로 해결되는 범위 | 남는 공백 | Freeway가 제안하는 해결 |
| --- | --- | --- | --- | --- |
| P1 무료 접근 경로의 분산 | 다른 서비스에서는 무료인 모델을 같은 작업 흐름에서 쓰기 어렵다 | OpenRouter가 제공하는 모델·공급처와 지원 BYOK 경로 | 외부 서비스가 자기 CLI에만 제공하는 무료 권한은 일반 API 키 등록과 다르다 | 공식 인터페이스로 연결 가능한 외부 무료 경로를 추가하고, API·텍스트·작업 위임을 구분한다 |
| P2 무료 사용 상태의 분산 | 어느 서비스가 지금 사용 가능하고 언제 다시 열리는지 따로 확인한다 | OpenRouter 내부 한도·공급처 상태와 실패 대체 | 여러 외부 서비스의 개인 인증·공유 한도·리셋 상태를 함께 운영해야 한다 | 공식 조회·로컬 관측·알 수 없음을 구분하고, 사용 가능한 독립 경로를 선택한다 |
| P3 반복되는 연결과 선택 작업 | 로그인·모델 선택·한도 오류·다른 도구 실행을 반복한다 | OpenRouter 한 경로로 통일할 수 있는 클라이언트의 설정 | 외부 전용 무료 경로까지 포함하면 연결·복구·선택 이유가 도구마다 흩어진다 | 한 CLI에서 연결·상태·선호 순서·제외 이유·재연결 동작을 제공한다 |

이 표의 “공백”은 우리가 선택한 사용 목적에 대한 범위 차이다. OpenRouter 자체의 모든 사용자에게 결함이라는 뜻은 아니다. P1의 실제 연동이 불가능하면 P2·P3만으로 새 제품을 만들 가치가 있는지 다시 판단해야 한다.

## P1의 근거와 실제 요청 결과

2026년 11월 16일 확인한 Cline 공식 무료 모델 안내는 무료 사용을 IDE와 CLI로 제한하고 API에서는 지원하지 않는다고 명시한다. OpenCode 공식 모델 안내도 무료 계층의 채팅 모델에는 OpenCode가 필요하다고 명시한다. 이것이 외부 무료 권한을 OpenRouter의 일반 API 경로와 동일하게 취급할 수 없는 구체적인 사례다. [Cline 무료 모델](https://docs.cline.bot/getting-started/free-models), [OpenCode 모델](https://opencode.ai/docs/console/models/)

실제 OpenCode 공식 서버는 연결과 무료 모델 조회에 성공했고, DeepSeek 요청에는 무료 할당 소진을 반환했다. Cline은 재로그인을 완료한 뒤 해당 DeepSeek에서 model not found를 반환했고 공식 CLI는 프로모션 종료 안내를 표시했다. 이 두 경로를 현재 응답 가능한 무료 경로로 표시하지 않는다. 현재 OpenCode 브리지는 도구를 차단한 텍스트 경로다. 상세 입출력은 [실증 결과](19-live-validation.md)를 따른다.

## 한도 전환으로 해결되는 것과 해결되지 않는 것

예를 들어 사용자가 허용한 외부 경로 A가 한도에 걸렸다고 하자. 별도의 무료 할당을 가진 경로 B가 같은 요청 계약을 충족하면 Freeway는 첫 응답을 보내기 전에 B를 시도할 수 있다. 사용자가 모델을 고정했으면 같은 모델 정체성을 지키고, Auto를 선택했을 때만 허용된 다른 모델을 고려한다.

A와 B가 같은 계정·IP·상위 무료 풀을 공유하면 이름만 바꿔도 한도는 늘지 않는다. 사용할 수 있는 독립 경로가 없으면 종료하고 대기나 재연결을 안내한다. OpenCode에서 진행하던 에이전트의 내부 상태를 Cline으로 그대로 옮겨 계속 코딩하는 기능은 별도 문제이며 초기 약속에 포함하지 않는다.

## 무료 비용 통제는 기본 조건

사용자가 무료 정책을 선택하면 주 요청과 Freeway가 통제하는 보조 요청 모두에 가격·권한 조건을 적용하고, 유료 또는 비용 근거가 불명확한 후보는 실행 전에 제외한다. 이 정책은 제품의 신뢰 조건이지 OpenRouter에 가격 제한 기능이 없다는 주장이 아니다.

앞서 확인한 Ori의 유료 보조 호출은 해당 클라이언트 실행의 관측이다. 이를 OpenRouter 전체가 무료 요청에 숨은 비용을 붙인다고 일반화하지 않는다. 외부 CLI를 통제할 수 없다면 “전체 비용 0 보장” 경로로 활성화하지 않는다.

# 차별점부터 확인하는 첫 구현

## 첫 통합 시험

첫 시험은 무료 경로 두 개의 이름을 나열하는 것이 아니라 **동일한 요청 계약을 만족하는 서로 독립된 무료 경로 두 개**를 실제로 실행하는 것이다. 그중 적어도 하나는 OpenRouter 밖에서 필요한 무료 권한을 제공해야 한다. 외부 경로의 존재, 공식 연동 가능성, 전체 실행 비용과 기능 보존을 함께 기록한다.

| 순서 | A가 제출할 것 | B가 제출할 것 | 통과 증거 |
| --- | --- | --- | --- |
| 1 대표 경로 실증 | 모델·무료 조건·공식 연결 방법·실제 응답·기능표 | OpenRouter 설정만으로 대체 가능한지 비교 | 외부 경로의 추가 가치 또는 제외 근거 |
| 2 공통 계약 확정 | 경로별 제약과 실제 이벤트 fixture | Route·기능·오류·이벤트·한도 스키마와 가짜 어댑터 | 같은 요청을 같은 계약으로 표현 |
| 3 두 경로 연결 | 계약을 통과하는 어댑터 두 개 | 선택·예약·실행·정산 코어 | 두 경로의 단독 성공과 독립 한도 근거 |
| 4 실패 전환 | 429·만료·취소의 공급처 fixture | 첫 이벤트 전 전환과 시작 후 중단 규칙 | 오류 주입 시험과 경로 추적 |
| 5 사용자 흐름 | 연결·상태·선호·복구 CLI와 안내 | 상태·선택 이유 API와 진단 기록 | 사용자가 한 번 연결한 뒤 경로별 설정을 반복하지 않고 실행 |

OpenRouter의 실제 429 대조군과 다른 무료 모델의 성공 응답은 19번에 기록했다. Freeway 자체의 전환은 같은 오류 fixture로 검사하고 실제 연동 결과와 구분한다.

## 세 가지 종료 판정

1. **진행:** 외부 무료 경로의 필요성과 공식 연동·기능 보존이 확인되고, 두 독립 경로에서 사용자 조작을 줄이는 결과가 있다.
2. **축소:** 텍스트 계약만 성립하면 텍스트 실행 도구로 범위를 줄인다. 도구 호출 API나 에이전트 연속 실행을 지원한다고 쓰지 않는다.
3. **보류 또는 기존 도구 사용:** 원하는 경로가 OpenRouter 설정만으로 충분하거나 외부 무료 권한을 공식적으로 연결할 수 없으면 코어 확대를 멈춘다.

등록한 업체 수와 태스크 수는 진행 판정의 증거가 아니다. 72개 태스크는 진행 시 사용할 작업 목록이며, 검증 전에 전부 구현하겠다는 약속이 아니다.

# 분업의 단일 책임과 인계 계약

## 역할을 나누는 한 문장

**A는 외부 서비스를 연결하고 사용자가 쓰게 만드는 담당이다. B는 연결된 경로 중 무엇을 언제 실행할지 결정하고 상태와 출시 품질을 보장하는 담당이다.** A·B는 현재 역할명이며 실명 배정은 회의에서 확정한다. 아래 내용은 확정 요청에 사용할 분업 제안이다.

## 기능별 최종 작성 책임

| 기능 | 최종 작성 책임자 | 직접 맡는 범위 | 상대방에게 넘기는 것 | 상대방이 하지 않는 일 |
| --- | --- | --- | --- | --- |
| 공급처 조사·무료 근거 | A | 공식 자료·실제 호출·모델 정체성·기간·권한 확인 | 경로 등록 자료와 증거 | B가 조사되지 않은 무료 조건을 추측하지 않는다 |
| 공식 로그인·공급처 연결 | A | 로그인·키 입력·만료 감지·재연결·공급처별 환경 구성 | 비밀 참조와 인증 상태 | B가 공급처 로그인 화면·토큰 갱신 특례를 구현하지 않는다 |
| 어댑터 | A | 공급처 요청·이벤트 변환·오류 변환·취소·usage·fixture | 공통 계약을 통과한 어댑터 | A가 다음 공급처 선택을 넣지 않는다 |
| 계약·로컬 인증·비밀 저장 | B | 스키마·오류·이벤트·로컬 API 인증·키 저장·마스킹 공통 규칙 | 버전 있는 계약·저장 API·샘플 | A가 별도 비밀 저장소나 로컬 API 인증 체계를 만들지 않는다 |
| 공급처 한도 해석 | A | 계정·IP·모델 풀 범위·단위·리셋·공식 조회 | 정규화된 한도 관측 | A가 공용 잔여량을 직접 차감하지 않는다 |
| 한도 계산·예약·저장 | B | 공유 범위·원자적 예약·정산·쿨다운·잠금·복구 | 읽기 전용 상태와 예약 결과 | UI와 어댑터가 상태 파일을 직접 갱신하지 않는다 |
| 경로 선택·실행·대체 | B | 기능·비용 필터·순서·예산·전환·취소·선택 이유 | 실행 API와 추적 | A가 UI 안에 별도 라우터를 만들지 않는다 |
| 외부 API·MCP·대화 기록 | B | 계약 검증·SSE·도구 호출·오류·작업 상태·대화 저장 | 클라이언트 계약과 예제 | A가 프로토콜·기록 형식을 독자 변경하지 않는다 |
| CLI·TUI | A | 연결·모델·우선순위 편집·상태·스트림·복구 표시 | 사용자 흐름과 재현 결과 | UI가 공급처를 직접 호출하거나 예약하지 않는다 |
| 사용자 docs | A | README·빠른 시작·공급처·CLI·설치·문제 해결 | 실제 버전으로 수행한 안내 | 사용자 문서에 미검증 공급처를 지원으로 표시하지 않는다 |
| API·개발·데이터 docs | B | API·어댑터·기능표의 공통 규칙·비용·저장·복구 | 계약과 일치하는 참고 문서 | A가 내부 계약을 추측해 중복 작성하지 않는다 |
| 패키징·설치기 | A | 포함 파일·런타임·설치·PATH·업데이트·제거·깨끗한 OS 시험 | 버전별 패키징 명령과 설치 결과 | A가 데이터 스키마 변환을 독자 구현하지 않는다 |
| 데이터 이전·복구 규칙 | B | 잠금·일관 백업·키와 암호문 보존·복호화 확인·스키마 복구 | 설치기가 호출할 이전·검증 계약 | 설치기가 사용자 데이터를 덮어쓰지 않는다 |
| CI·릴리스 | B | A의 패키징 명령 실행·검사·버전·체크섬·후보·게시 절차·변경 안내 | 검사한 후보 묶음과 출시 기록 | B가 별도의 설치기와 패키지 파일 목록을 중복 구현하지 않는다 |

검토자가 있다는 이유로 작성 책임을 공동으로 돌리지 않는다. 공급처에서 발생한 원본 응답·모델명·로그인 문제는 A가 재현하고 고친다. 공통 스키마·선택·예약·프로토콜 문제는 B가 재현하고 고친다. 한 이슈가 두 계층에 걸치면 최초 실패한 계약을 기준으로 태스크를 둘로 나누고 각 책임자를 유지한다.

## 파일과 인터페이스의 소유권

초기 코드 기준으로 A는 `catalog.mjs`, 공급처 어댑터 영역, `opencode.mjs`, `cli.mjs`, `tui.mjs`, 설치 스크립트를 맡는다. B는 `engine.mjs`, `store.mjs`, `server.mjs`, MCP·대화 저장, 공통 계약과 CI를 맡는다. 실제 파일 위치와 호출 관계는 [현재 코드 지도](04-current-code-and-gaps.md)를 따른다.

하나의 파일에 책임이 섞여 있으면 조사 없이 대규모 분리를 하지 않는다. 먼저 파일 작성자 한 명을 정하고 상대 변경은 계약·fixture로 전달한다. 새 공통 계약의 작성 책임은 B이고 A가 실제 공급처로 검토한다. 패키지에 무엇을 포함할지와 패키징 명령은 A가 작성하고, CI에서 그 명령을 실행하고 버전·체크섬을 검증하는 코드는 B가 작성한다.

## A가 B에게 넘기는 최소 묶음

| 인계 항목 | 반드시 들어갈 내용 | B의 수락 조건 |
| --- | --- | --- |
| 경로 정의 | 모델 버전·변형·실행 계약·인증 참조·무료 근거와 확인일 | 필수 필드와 모델 정체성이 검증된다 |
| 기능·한도 관측 | 지원·미지원·미확인, 한도 범위·리셋·조회 출처 | 공통 기능·한도 스키마를 통과한다 |
| 어댑터와 fixture | 정상·429·만료·시간 초과·취소·부분 스트림·usage | 동일 fixture를 코어 계약 검사에서 재생할 수 있다 |
| 실제 호출 근거 | 사용한 버전·모델·상태·정리한 응답·비용 검증 범위 | 키·원문 비밀 없이 성공·실패·보류가 구분된다 |

## B가 A에게 넘기는 최소 묶음

| 인계 항목 | 반드시 들어갈 내용 | A의 수락 조건 |
| --- | --- | --- |
| 계약과 가짜 서버 | 버전·예시 요청·이벤트·오류·종료·취소 | 실제 공급처 없이 CLI와 어댑터를 개발할 수 있다 |
| 상태와 explain | 인증 상태·선택 이유·제외 이유·한도 출처·확인 시각 | UI가 추측하거나 상태 파일을 읽지 않고 표시한다 |
| 실행 결과 | 요청·시도 ID·실제 경로·모델·스트림·usage·비용 상태 | 시작·취소·실패·완료를 구분해 표시한다 |
| 출시 후보 | 버전·체크섬·지원표·알려진 제한·복구 절차 | A가 문서대로 설치·요청·업데이트·복구한다 |

## 검증과 출시의 결함 담당

| 실패한 지점 | 수정 책임 | 재검증 책임 | 완료 증거 |
| --- | --- | --- | --- |
| 로그인·모델 조회·공급처 변환 | A | A 실제 호출, B 계약 회귀 | 비밀 없는 probe와 fixture |
| 라우팅·예약·정산·SSE·로컬 인증 | B | B 자동 시험, A 사용자 흐름 | 장애·경쟁·취소 시험 결과 |
| CLI 표시·명령·사용자 안내 | A | A 깨끗한 사용자 흐름, B 계약 대조 | 도움말과 실행 결과 일치 |
| 설치·PATH·런타임·패키지 파일 목록 | A | A 깨끗한 OS, B CI 재생 | 설치·업데이트·제거 결과 |
| 키·상태·대화 이전과 복구 | B | B 암호화 데이터 시험, A 설치 통합 | 원본 보존·복호화·복구 결과 |
| CI·버전·체크섬·릴리스 후보 | B | B 자동 검사, A 후보 설치 | 시험한 파일과 게시 후보의 일치 |

최종 게시 담당은 B로 제안한다. A의 새 환경 설치·복구 확인과 B의 코어·비밀·산출물 검사가 모두 있어야 후보를 통과시킨다. 여기서 정한 것은 역할과 절차이며 실제 배포를 실행한 것은 아니다.

## 72개 태스크와 연결하는 방법

[계층별 작업 분해](16-work-breakdown.md)의 각 태스크에는 P1·P2·P3 또는 E0 기반 작업의 연결을 표시한다. E0은 계약·보안·검사·문서·배포처럼 해결을 운영 가능한 제품으로 만드는 작업이며 차별점으로 계산하지 않는다. 각 태스크의 담당자가 위 책임표와 충돌하면 공동 담당으로 덮지 않고 작성 범위를 나눈다.

처음에는 W01·W02.01의 범위·증거와 W03의 계약만 우선 진행한다. 첫 외부 경로의 가치와 자동화 가능성을 확인한 뒤 필요한 W04 이후 작업을 활성화한다. 언어 전환, 전면 TUI 재작성, 모든 후보 연결은 이 판정의 선행 조건이 아니다.
